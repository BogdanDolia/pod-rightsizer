From test to review

A clear path from
usage to configuration.

Designed for engineers who need to understand where the numbers came from.

  1. 01

    Choose the workload

    Name the namespace, Deployment, and container. Keep the service URL separate from the object you measure.

  2. 02

    Run a measured load test

    Set RPS or concurrency. Recommendations require the test to meet throughput, HTTP error-rate, and p95 latency thresholds.

  3. 03

    Inspect the evidence

    Review CPU percentiles, memory high-water, independent sample count, policy, and the comparison with current settings.

  4. 04

    Review the proposed change

    The generated patch must pass Kubernetes server-side dry-run. You decide when and how to apply it.

Make the calculation tangible

Explore a resource policy.

A fixed sample: CPU p95 = 180m, memory high-water = 145Mi. Adjust the buffers to see the generated values.

Policy inputs

CPU limit policynone

CPU requests use the selected percentile. Memory requests use the observed high-water mark. Limits have separate policies.

example-resource-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  namespace: demo
  name: checkout-api
spec:
  template:
    spec:
      containers:
      - name: api
        resources:
          requests:
            cpu: "198m"
            memory: "174Mi"
          limits:
            cpu: null
            memory: "209Mi"

Browser-only illustration. This page does not connect to a cluster or validate a patch. A real recommendation requires workload metrics, applicable policy, and server-side dry-run.

Start with a service you know

Build. Measure. Review.

Use a representative test environment, a stable Deployment, and access to Kubernetes Metrics Server.

Read the full usage guide ↗
1. Build from source · Go 1.25+
git clone https://github.com/BogdanDolia/pod-rightsizer.git
cd pod-rightsizer
go build -o pod-rightsizer ./cmd/pod-rightsizer
2. Run against your workload
./pod-rightsizer \
  --target http://localhost:8080 \
  --namespace default \
  --deployment myservice-api \
  --container api \
  --duration 5m \
  --rps 50 \
  --output-format json

Expose the service URL first, for example with kubectl port-forward service/myservice 8080:80. The Kubernetes caller also needs Deployment patch permission for dry-run validation.

Understand the result

Measured evidence has a scope.

A passing test describes the workload under the measured conditions. Confidence reflects sample count and observation duration. Server-side dry-run checks the API request; performance with the proposed resources still needs validation in your environment.

The Advisor API also supports observing current workload metrics without generating HTTP load. Run it in your own environment — the public project website is a static guide.
